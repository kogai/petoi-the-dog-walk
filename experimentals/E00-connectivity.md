# E00: トークンを送ったときの応答の形式

- 状態: 依頼中
- 依頼日: 2026-09-25（2026-10-16 に [README](README.md) の「人が実行できる手順にする」に合わせて書き直した）
- 実施日: 2026-10-16（書き直す前の手順で、シリアル経路の一部。結果は下の「結果」節）
- 実施者: kogai

## 目的

Mac から Bittle へシリアル経由でトークンを送ったとき、Bittle が何を返すか（形式と時刻）と、
同じトークンの連続送信・歩行の継続がどう振る舞うかを記録する。
結果で、`SerialTransport`・`FakeTransport` の振る舞い（[06-transport.md](../docs/design/06-transport.md) 2節）と、
`serialport` クレートを Mac で使えるか（[D-09](../docs/design/decisions.md)）が決まる。

2026-10-16 の実施で、A-1〜A-3・A-7・A-8 の判定は済んだ（「結果」節）。**今回お願いするのは A-4・A-5・A-6 だけ。**

この手順書で確かめないこと:

- Wi-Fi 経路（書き直す前の手順 B。`HttpTransport` の判定）。新しい ID を付けた別の実験として依頼する（ID はその依頼の PR で決める）。
- 停止トークン `d` で止まるか。今の道具は問いを出してから `d` を送るので、`d` の後の様子を問えない。道具を直してから、別の実験として依頼する。
- 送信間隔の下限の既定値（[06-transport.md](../docs/design/06-transport.md) 2節）。A-4 の値は記録するが、下限はこの実験では決めない。

## 必要なもの

- 人数と役目: 1人（Bittle は床に置いたまま扱う。持ち上げない）
- 機材: Bittle（標準ファーム。**脚を付けていない状態**で行う。脚を付けた後は、この手順書では行わない）、USB アダプタ、充電した電池、Mac
- ソフトウェア: mise と Rust（準備の P-0 で入れる、または確かめる）、このリポジトリ
- 所要時間の目安: 30分（P-0 で Rust を初めて入れるときは、さらに十数分）

## 安全上の注意

- Bittle を平らな床に置き、周囲 2m 以内に物・段差が無いことを確認する。台の上では行わない。
- **Bittle は床に置いたまま、持ち上げない。** 脚が付いていないので、歩き方のトークンを送ってもその場から動かない（サーボだけが動く）。
- 道具（`e00-serial-probe`）は、終わるとき・エラーのとき・`Ctrl-C` を押したとき・ターミナルを閉じたときに停止トークン `d` を送る。
  `d` を送れなかったときは `!! STOP TOKEN NOT SENT` と表示する。**その表示が出たら、すぐ電源を切る。**
  `d` でシリアル経由で止まるかどうかは**未確認**。止まらなければ電源を切る。
- **`Ctrl-Z` は使わない**（道具が一時停止し、`d` が送られないまま動き続ける）。止めるときは `Ctrl-C`。
- **`Ctrl-S` は押さない**。ターミナルの表示が止まり、道具の送信も止まる（Bittle は最後の動作を続ける）。表示が止まったら、**まず `Ctrl-C` を押し**（このとき道具は `d` を送り、それ以降のトークンは送らない）、それから `Ctrl-Q` で表示を戻す。
- 道具は、予定の終わり（`E00_ASK` を付けたときは、問いを見る 1.5 秒の後）から 3 秒たっても `d` を送っていなければ、自分で `d` を送り、それ以降のトークンは送らない。この `d` は送った瞬間には画面に出ない（終わるときに `the watchdog sent the stop token` と表示する）。サーボの動きで止まったかを確かめ、止まらなければ電源を切る。
- 上の 3 秒の見張りが送った `d` は、ログに `->` の行として残らない。`Ctrl-C` のときは `-> "d"` の行が残るが、その時刻は、実際に最初に `d` を送った時刻より遅れる。そのため、ログに対応する `->` の無い `<-` の行が出ることがある。
- 起動時に `no independent stop path, refusing to run` と表示されたら、道具は `d` だけを送って終わる（トークンは送らない）。その回は実施できなかったとして記録する。

## 準備

コマンドは、リポジトリのルート（`Cargo.toml` がある場所）で実行する。各手順の出力は `E00_LOG=<ファイル>` で `experimentals/raw/` に保存する（このフォルダの中身はコミットされない。`tee` は使わない）。道具は同じ名前のファイルを上書きするので、やり直すときは名前の末尾に `-r2`・`-r3` のように番号を付け（例: `e00-a6-r2.txt`）、前の回のファイルを残す。

- P-0. Rust を使えるようにする。2026-10-16 の実施で用意した Mac なら、確かめるだけでよい。
  - 初めての Mac: Xcode Command Line Tools（無ければ `xcode-select --install`）と [mise](https://mise.jdx.dev/getting-started.html) を入れる。mise は、Homebrew があれば `brew install mise` の後に `echo 'eval "$(mise activate zsh)"' >> ~/.zshrc`、無ければ `curl https://mise.run | sh` の後に `echo 'eval "$(~/.local/bin/mise activate zsh)"' >> ~/.zshrc`。新しいターミナルを開き、このリポジトリを clone したフォルダで `mise trust && mise install rust` を実行する。
  - 確かめ方: リポジトリのルートで `cargo --version` を実行し、`cargo 1.` で始まる行が表示される。
- P-1. Arduino IDE を終了する（シリアルモニタを閉じるだけでなく、IDE ごと）。ポートは一度に1つのプログラムしか開けない。
  確かめ方: Dock の Arduino IDE のアイコンの下に点が無い。見落としても、P-6 で `cannot open` と表示されれば分かる（そのときは IDE を終了してやり直す）。
- P-2. 道具をビルドする。`E00_ASK` が入った版が要るので、前にビルドした人もビルドし直す。
  ```sh
  git pull
  cargo build --release -p walk-experiments --bin e00-serial-probe
  ```
  確かめ方: 最後に `Finished` と表示される。
- P-3. 電池を充電し、Bittle に付ける。USB アダプタで Mac とつなぎ、Bittle の電源を入れる。
- P-4. 置き方を決める。Bittle は床、USB はつないだまま。Mac は、画面から目を移すだけで Bittle の前脚付近（首の後ろの肩のあたり）が見える位置に置く（例: 床に座って、Mac を膝の前、Bittle をその向こうに置く）。
  確かめ方: 画面を見た姿勢のまま、目だけを動かして前脚付近のサーボが見える。
- P-5. ポートを調べ、起動を待つ時間を設定する。**ポート名は結果に貼らない。**
  ```sh
  ./target/release/e00-serial-probe --list
  export E00_SETTLE_MS=8000
  echo "$E00_SETTLE_MS"
  ```
  確かめ方: `usbserial` を含む `/dev/cu.` の行がある。それを `<PORT>` として以降のコマンドに使う。最後に `8000` と表示される。
  `usbserial` の行が無ければ、USB を挿し直して、もう一度実行する。それでも無ければ「ポートが見つからない」と記録して止める。新しいターミナルを開いたときは、`export` からもう一度行う。
- P-6. 起動と電池を確かめる。
  ```sh
  E00_LOG=experimentals/raw/e00-p6.txt ./target/release/e00-serial-probe <PORT> kbalance
  ```
  確かめ方（出力だけを見る）: `* Start *` を含む `<-` の行が1つだけ。`Ready!` の行が、最初の `-> "kbalance"` より前に出ている。`Low power` の行が出ていない。
  - `* Start *` が2つ以上ある（起動中に再起動した）か、`Low power` が出たら、電池を充電してから P-6 をやり直す。
  - それ以外で `Ready!` が `->` より後に出たら、`export E00_SETTLE_MS=10000` にしてやり直す。10000 でも後に出たら「起動が遅い」と記録して止める。

## 手順

判定は、A-4・A-5 は道具の出力（`->` と `<-` の時刻）だけで行う。人が見るのは A-6 の問い1つだけ。

**どの手順でも**、出力に `* Start *` を含む行が2つ以上ある回（実行中に再起動した）と、`Low power` の行がある回は使わない。電池を充電し、P-6 を通してから、その回をやり直す。

### A-1〜A-3・A-7・A-8（実施済み）

2026-10-16 に実施し、判定した（「結果」節）。再実施は要らない。

### A-4. トークンごとに `k` が返るまでの時間

トークンを1回の実行で1つだけ送り、`k` が返るまでの時間を測る。観察は要らない。`khi` だけは、ばらつきを見るため3回測る。

```sh
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-ksit.txt ./target/release/e00-serial-probe <PORT> ksit
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-kbalance.txt ./target/release/e00-serial-probe <PORT> kbalance
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-kwkF.txt ./target/release/e00-serial-probe <PORT> kwkF
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-khi-1.txt ./target/release/e00-serial-probe <PORT> khi
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-khi-2.txt ./target/release/e00-serial-probe <PORT> khi
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a4-khi-3.txt ./target/release/e00-serial-probe <PORT> khi
```

それぞれ約 20 秒かかる（起動 8 秒 + 待ち 10 秒）。1つずつ実行し、終わってから次を実行する。

### A-5. 同じトークンを続けて送る

`khi` を 2 秒あけて2回送る（1回目の `khi` の動作中に2回目が届くように。2026-10-16 の実施では `khi` の `k` は約 5 秒後）。観察は要らない。A-4 の `khi` 1回のときと、`k` の数と時刻を比べる。

```sh
E00_WAIT_MS=2000 E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e00-a5.txt ./target/release/e00-serial-probe <PORT> khi khi
```

約 20 秒かかる（起動 8 秒 + 間隔 2 秒 + 待ち 10 秒）。

### A-6. 歩行は続くか

`kwkF` を送り、5 秒後に道具が問いを出す。この手順だけ、人が見る。
人が見る理由: 歩行中、ファームは周期的な出力を出さない（2026-10-16 の実施では、`kwkF` の後に出たのは `G`・`k`・`Low power` の行だけ）。そのため、5 秒後に歩行が続いているかは出力から分からない。

`E00_ASK` を実機で使うのはこれが初めて（**未実行**。偽のシリアルポートでだけ動作を確かめた）。問いが表示されない、文字化けするなど、道具がおかしいときはその回を使わず、「記録すること」の最後の項目に書く。

```sh
E00_FINAL_WAIT_MS=5000 E00_ASK='前脚付近のサーボは、今動いていますか？' E00_LOG=experimentals/raw/e00-a6.txt ./target/release/e00-serial-probe <PORT> kwkF
```

1. コマンドを実行したら、画面を見て待つ（Bittle を見ている必要はない）。
2. `>>> LOOK NOW:` が表示されたら、目を Bittle の前脚付近のサーボへ移す。ベルが鳴らないこともあるので、表示で判断する。
3. `>>> answer y (yes), n (no) or ? (could not tell), then press Enter:` が表示されたら、`y`・`n`・`?` のどれかを入力して Enter を押す。この時点で道具は `d` を送っている。
4. 答えが `answer: none` か `answer: interrupted` になった回、または `answer:` の行が無い回は使わず、やり直す。

## 判定基準

出力の時刻で判定する。

- 「`k` が返るまでの時間」は、`-> "<トークン>"` の時刻から、`k` の応答を受け取り終えた時刻まで。道具は受け取った塊ごとに `<-` の行を出すので、1つの応答が `"k\r"` と `"\n"` のように2行に分かれることも、他の文字列と同じ行に入ることもある。`->` より後の `<-` の行の中身を順につないで読み、最初に現れる `k\r\n` の最後の `\n` を含む `<-` 行の時刻を使う。`k` の数も、つないだ中身で数える。
- 「`khi` の範囲」は、A-4 の `khi` 3回の時間の最小から最大までを、両側に 0.3 秒ずつ広げた範囲。A-5 の「範囲に入る」の2行は、この範囲の幅が2回の送信の間隔（2 秒）より狭く、かつ A-4 の `khi` の `k` が3回とも 2 秒以上たってから返り、かつ範囲の上端の2倍が 12 秒（1回目の送信から道具が `d` を送るまでの時間）以下のときだけ使う。2回が順に実行されたときに、2つ目の `k` を `d` の前に受け取れるようにするため。そうでないときは、A-5 は分からなかったとする。
- 再起動や `Low power` で使わなかった回は、判定に入れない。

| 観察 | 結果 | 設計への影響 |
|---|---|---|
| 応答（A-4） | 6回すべてで `k` が返り、`kwkF` の `k` が 1 秒以内に返り、`khi` の `k` が3回とも 2 秒以上たってから返る | `k` は「動作を終えた（歩行は受け付けた）」しるしと読める。`SerialTransport::send` は `k` を待って成否を判定できる。待つ時間の上限は、A-4 の値をもとにトークンごとに決める |
| 応答（A-4） | どのトークン（`khi` の3回を含む）も 1 秒以内に `k` が返る | `k` は「受け付けた」しるし。`send` は `k`（と `?<名前>`）だけを短い時間待つ |
| 応答（A-4） | `k` が返らない回がある、または上のどちらにも当てはまらない | 分からなかった。安全側に倒し、送りっぱなしにして、送信間隔の下限だけで制御する。`?<名前>` の検出は別に決める |
| 連続送信（A-5） | `k` が1つだけで、1回目の送信から数えた時間は `khi` の範囲に入り、2回目の送信から数えた時間は入らない | 2回目は無視される。抑止は必須ではない（通信を減らすためだけに行う） |
| 連続送信（A-5） | `k` が1つだけで、2回目の送信から数えた時間は `khi` の範囲に入り、1回目から数えた時間は入らない。または `k` が2つ返る | 2回目でやり直しになるか、2回とも実行される。同じトークンの連続送信を必ず抑止する |

| 歩行（A-6） | `answer: yes`（5 秒後もまだ動いている） | 同じトークンを連続で送らない（06 の設計案どおり） |
| 歩行（A-6） | `answer: no`（5 秒より前に止まった） | 歩行中は一定間隔で再送する設計に変える |
| 歩行（A-6） | `answer: unknown`（分からなかった） | 分からなかった。保留。06 の歩行の扱いは決めずに、問いの時刻を変えて再依頼する |

| （全体） | 手順どおりに進まなかった、または再起動・`Low power` のために使える回が無かった | 再依頼する。それまで 06 の 2節の該当する部分は保留のまま |
