## 手順書の書き方

- [TEMPLATE.md](TEMPLATE.md) から作る。
- 人が一人で、コピー＆ペーストだけで進められるように書く。プレースホルダーは `<PORT>`、`<IP>` のように示す。
- 実行していないコマンドやプログラムには **未実行**、確かめていないトークンや API 名には **未確認** と書く（TEMPLATE の手順の例を参照）。
- 判定基準は、起こりうる結果ごとに、設計のどこがどう変わるかを書く。
- 実機を動かす手順には、止め方を必ず書く。
- 実験で使う道具は Rust で書き、ワークスペースの `walk-experiments` クレートに置く（検査・レビューの対象にするため）。例外は [07-roadmap.md](../docs/design/07-roadmap.md) の実験の一覧の注記にある。

### 人が実行できる手順にする

人は、動いているものを見ながら複数のことを覚えておけない。出力を読みながら Bittle を見ることもできない。手順はこの前提で書く。

- **判定は、記録に残るもので行う。** 道具の出力と、ログの時刻で判定できるように手順を組む。人の目で見たことを判定の根拠にするのは、出力では判定できないときだけにし、その理由を手順書に書く。
- **観察の問いは、1回の実行につき1つ。** その場で答えられる「はい／いいえ」にし、「分からない」も答えとして認める。速さ・順番・回数・「最初からやり直したか」のように、動きを覚えておかないと答えられない問いは書かない。
- **問いは道具に出させる。** 見るべき瞬間に道具が問いを表示し、答えをログに残す（例: `e00-serial-probe` の `E00_ASK`。今は、最後の待ち時間の後に1回だけ問える。`E00_ASK_AFTER_STOP_MS` を付けると、`d` を送った後に問える）。手順書の文で「A の後に B を見る」「`->` が出たら～を見る」と書かない。人は、表示が出るまで画面を見て待ち、出たら Bittle を見る。問いは、そのときの状態だけを聞く（例: 「まだ動いていますか」）。
- **問いを出せる道具が無いときは、** 先に道具へ問いの機能を足す（別の PR）。足せないなら、その観察はやめて、出力だけで判定できる形にする。
- **人に2つのことを同時にさせない。** 画面を読みながら Bittle を見る、Bittle を持ちながらキーボードを打つ、などを求めない。必要なら2人で行うと書き、それぞれの役目を分ける（例: 1人が画面を見て「今」と声をかけ、もう1人が Bittle を見て答える）。
- **観察ごとに、判定基準に「分からなかった」の行を置く。** 「分からなかった」は失敗ではなく、正しい結果の1つとして扱う。設計への影響は、観察ごとに「安全側の設計に倒す」か「保留」のどちらかを選んで書く。道具の答えが yes・no・unknown のどれでもないとき（`answer: none`、`answer: interrupted`、`answer:` の行が無い）は、その回を使わず、やり直す。
- **準備は手順の最初に書き、できているかの確かめ方も書く。** 例: Bittle をつないで電源を入れてから `--list` でポートを調べ、つなぐ前より行が増えたことを確かめる（USB なら `usbserial` を含む行）。待ち時間は `export E00_SETTLE_MS=8000` の後に `echo "$E00_SETTLE_MS"` を実行し、`8000` と表示されることを確かめる。

E00 と E01 は 2026-10-16 に、このルールに合わせて書き直した。

このルールより前に実施した結果を記録する `[実験結果]` の PR、状態だけを変える PR、この注記を足す PR は、手順の本文を変えないので、このルールでは止めない。ルールより前の結果に、今のルールに合わない手順（書き直す前の E00・E01 の、人が動きを見て答える手順など）の観察が含まれていても、記録はしてよい。ただし、判定基準のその行は判定に使わない。

## 共通の注意（実施する人へ）

- 実機を動かすときは、Bittle を平らな床に置き、周囲 2m 以内に物・段差が無い場所で行う。台の上では行わない。
- 動作がおかしいときは、**電源を切る**。これが確実な止め方。
  停止トークン `d` でも止まる見込みだが、シリアルでどう働くかはまだ確かめていない（E00 では確かめない。道具を直してから別の実験で確かめる）。`d` の送り方は各手順書の「安全上の注意」に書く。
- **このリポジトリは公開されている。** 結果を貼る前に、API キー・IP アドレス・シリアルポート名・PC 名・ユーザー名・ホームのパス・機器のシリアル番号を `<IP>`、`<PORT>` のように伏せる（[public-repo.md](../docs/rules/public-repo.md)）。エラーの表示にはホームのパスやポート名が入りやすい。
- 生の出力は `experimentals/raw/` に保存する。このフォルダの中身はコミットされない（フォルダ自体は `.gitkeep` でリポジトリにある）。
- API キーは環境変数で渡し、ファイルや結果に書かない。使った後は、結果に含まれていないことを [public-repo.md](../docs/rules/public-repo.md) 3節の方法で確かめる。
- 写真や動画を載せるときは、部屋の様子や人が写っていないか確かめる。
- 実行したコマンドと、出力をそのまま（伏せた上で）貼る。要約だけにしない。
- 結果は、手順書の「結果」節を埋める `[実験結果]` の PR で送る。PR や issue のコメントに貼ってもよい。その場合は、エージェントが `[実験結果]` の PR を作って転記する。
