# E13: 停止トークン `d` で、動作が打ち切られるか

## 目的

脚を付けた Bittle で、長い動作（`khi`）の途中で停止トークン `d` を送ったとき、その動作が打ち切られるかを、道具の出力だけで確かめる。あわせて、`d` を2回続けて送ったときの応答を記録する。

結果で決まること:

- `d` を停止に使ってよいか（[06-transport.md](../docs/design/06-transport.md) 2節、[ADR-0001](../docs/design/adr/0001-driver-layer.md) 2.6節 S1）。フェーズ 1c（[07](../docs/design/07-roadmap.md)）の前提の一部。
- `d` を2回送っても害が無いか（ADR-0001 S3。今は確かめないまま、送ってよいことにしている）。

### 出力で判定する理由と、判定に使う事実・推論

最初の実施（「結果」節）では、`kwkF`（歩き方）を送ってから問いを出し、サーボが動いているかを人に答えてもらった。しかし答えは `d` の後に入力される組み方で、`kwkF` が自分で止まる時刻とも重なりうるので、止まった原因を見分けられなかった。そこで、終わったときに `k` が返る動作 `khi` を使い、出力だけで判定する。

- 事実: `khi` を送ると、約 5.5 秒後に `k` が返る（F-B11。5486／5506／5503 ms の3回。脚を付けていない状態）。
- 事実: `khi` を 2 秒あけて2回送ると、`k` は1つだけ返った。1回目の送信から 8604 ms、2回目から 6597 ms で、`khi` 1回分とは合わない（F-B13。1回のみ。脚を付けていない状態）。
- 注意: 上の2つは脚を付けていない状態の結果である。脚を付けると、サーボの負荷が変わり、`k` が返るまでの時間が違う見込みがある（推論）。そのため、時刻の範囲は F-B11 の値を使わず、今日の対照（C-1）で測る。
- 推論（ファームのソースコードから。OpenCat、コミット `24563ca` の [skill.h](https://github.com/PetoiCamp/OpenCat/blob/24563ca2e0218150f6299d013cd3a20c45433467/src/skill.h) の `perform()` と [reaction.h](https://github.com/PetoiCamp/OpenCat/blob/24563ca2e0218150f6299d013cd3a20c45433467/src/reaction.h) の末尾。基板では**未確認**）: `khi` のような動作（ソースでは period が負の skill）は、1コマごとに受信を確かめる。何か届いていれば、`up` の姿勢に切り替えて動作をやめ、その動作の `k` は出さない。その後、届いたトークンを処理する。F-B13 の「`k` が1つだけ」は、この読みと合う。
- 推論（同じソース。reaction.h の `T_REST`）: `d` を受けると、休む姿勢にしてサーボの力を切り、`g` と `d` を返す。起動の後にファームが自分で出す `g\r\nd\r\n`（F-B9）は、この経路の出力と合う。
- 推論（F-B19。公式のコードの `read_serial` の読み方）: ファームは、待っている最初の1バイトをトークンにし、続くバイトをその引数として読む。E00 で道具の停止に返った `\n\r\n` は、道具が `"\nd\n"` を送っていたため、`\n` というトークンとして読まれた応答と読める。道具は #27 で、停止に `d\n` だけを送るように直した。そのため、この実験の `d`（トークンとして送るものも、道具が終わるときに送るものも）への応答は、E00 と違ってよい。
- 注意: ソースの読みが基板のファームと合うかは確かめていない。そのため判定は、ソースの読みだけに頼らず、`khi` の `k` が返る時刻と、`d` への応答が届く時刻の両方で行う。

これらから、`khi` の途中で `d` を送ったとき、

- `khi` の `k` が予定の時刻（対照の C-1 で測る）に返り、`d` への応答がその後に届けば、`d` は `khi` が終わるまで待たされ、`khi` は最後まで続いたと読める。
- `k` が1つも返らず、`d` への応答が `d` のすぐ後に届けば、`khi` は途中で打ち切られたと読める（推論。`k` が出ない理由は、ほかにもありうる。そのため、対照の C-1 で `k` が毎回返ることを先に確かめ、`d` への応答の時刻も合わせて見る）。
- それ以外（範囲の外で `k` が返る、など）は、どちらとも読めるので「分からなかった」とする。

この実験では確かめないこと:

- 歩き方（`kwkF` など）を `d` で止められるか。歩き方の `k` は受け付けたときに返る見込み（F-B11 の時間、06 2.1節の推論）で、出力からは止まったかが分からない。脚を付けた状態で E14 で確かめる（07 の E14 の行）。フェーズ 1c に進むには、E14 の結果も要る。
- 止まるまでのミリ秒単位の遅れ。
- 脚を付けていない状態との比べ。2026-10-16 の版は脚を付けていない状態で行う予定だったが、実施は中止になり、判定に使える結果は無い（「結果」節）。
- `d` で止まった後の姿勢が正しいか（休む姿勢になったか）。人の目が要るので、この実験では問わない。

## 安全上の注意

- Bittle を平らな床に置き、周囲 2m 以内に物・段差が無いことを確認する。台の上では行わない。
- **脚が付いているので、Bittle は体ごと動く。** 道具を実行している間は、Bittle とケーブルに触らず、手を離しておく。持ち上げない（例外は、道具が終わってサーボが止まった後の置き直しだけ。共通の決まり）。指をサーボや脚の関節に近づけない（挟まれるおそれがある。推論）。
- 動作の見込み（推論。**未確認**）: `kbalance` で立ち、`khi`（hello。F-T1）で座って前脚を振る、`d` で休む姿勢へ動いてサーボの力が切れる。動作の途中で姿勢が変わるので、Bittle が倒れることがありうる。倒れたら、ファームが起き上がりの動き（`rc`）を始めることがある（E01 の「使うトークン」の推論）。どちらも、道具が終わるまで触らない。
- 床で滑ったり向きが変わったりして、2m の範囲から出そうになったら、まず `Ctrl-C` を押す（道具が `d` を送って終わる）。それでも動いていたら、電源を切る（次の項目）。
- 道具（`e00-serial-probe`）は、終わるとき・エラーのとき・`Ctrl-C` を押したとき・ターミナルを閉じたときに `d` を送る。
- 道具が終わった後もサーボが動き続けていたら、電池のボタンを長押しして電源を切る（準備の P-4 で確かめる）。それでも動いていたら、USB のケーブルも抜く。動いている脚に手を近づけないよう、ボタンには横か後ろから手を伸ばす。
- `!! STOP TOKEN NOT SENT` と表示されたら、すぐ電源を切る。
- **`Ctrl-Z` は使わない**（道具が一時停止し、`d` が送られないまま動き続ける）。止めるときは `Ctrl-C`。
- **`Ctrl-S` は押さない**。ターミナルの表示が止まる。止まったら、まず `Ctrl-C` を押し、それから `Ctrl-Q` で表示を戻す。
- 起動時に `no independent stop path, refusing to run` と表示されたら、道具は `d` だけを送って終わる。その回は実施できなかったとして記録する。

## 手順

### 共通の決まり

- 判定はすべて道具の出力（`->` と `<-` の時刻と中身）で行う。人が見て答える問いは無い。実施する人は、出力を貼るだけでよい。時刻を測ったり数えたりするのは、エージェントが行う。
- 道具は改行ごとではなく、受け取った塊ごとに `<-` の行を出す。1つの語が2つの `<-` の行に分かれることがある（例: `* St` と `art *`）。そのため、下の確かめは、`<-` の中身を受け取った順につないだものに対して行う（P-5 の数えるコマンドと同じ）。見える形（`\r\n` など）は塊ごとに作られるので、つなぐだけでよい。
- 次のどれかに当たる回は使わない。当たるかはエージェントが確かめ、当たったら、電池の充電と P-5 からのやり直しを依頼する。
  - つないだ中身に、`* Start *` が2つ以上ある回（途中で再起動した。F-B15）。ただし C-3 で、最初の `->` より後にだけ2つ目が出た回は、捨てずに記録して判定に使う（C-3 の節）
  - `Ready!\r\n` が、最初の `->` より前に届いていない回（F-B9）
  - つないだ中身に `Low power` がある回
- `read error:` で始まる行がある回も使わない（受信が途中で止まり、その後の `k` や応答を見られないため）。判定基準の「道具」の行に従う。
- 「`d` への応答の時刻」は、C-2・C-3 でトークンとして送った `d` の `->` の時刻から、その後の `<-` の中身をつないだもののうち、`d` への応答の最初の文字を含む `<-` の行の時刻まで。`d` の後の中身が `k\r\n` で始まるときは、それを `khi` の `k` として扱い、`k\r\n` より後に現れる最初の文字を `d` への応答の始まりとする。
- 「`k` の時刻」は、`k` で始まるトークンの `->` の時刻から、その後の `<-` の中身をつないで最初に現れる `k\r\n` の、`\n` を含む `<-` の行の時刻まで（E00 の判定基準と同じ）。起動の表示の先頭の `k`（最初の `->` より前）は数えない。
- 1つずつ実行し、道具が終わってから次を実行する。
- 道具が終わるたびに、Bittle を1回だけ見て、倒れているか（横倒し・裏返し）を確かめる（道具の実行中は見なくてよい）。倒れていたら、または倒れているか分からなければ（倒れたものとして扱う。安全側）、その場でその回のファイル名（例: `e13-c2-1`）をメモし、その回は使わない。倒れると、ファームの起き上がりの動き（`rc`）が `k` などを出し、`k` の時刻を読み違えるおそれがあるため（推論。**未確認**）。
- 次の回の前に、Bittle が4本の脚を下にして床に置かれていることを確かめる。そうでなければ、サーボが止まっている（音がしない）のを確かめてから、手で置き直す。触ってよいのは、このときだけ。道具はポートを開くたびに基板を起動し直し、起動したときに体が大きく傾いていると、休む姿勢でなくキャリブレーションの姿勢へ動く見込みがある（OpenCat のソース `24563ca` の `initRobot()` の読み。推論。**未確認**）。倒れた後に置き直した回は、P-5 からやり直す。

### C-1. 対照: `khi` だけを送る（2回）

今日の電池の状態で、`khi` の `k` が何秒で返るかを確かめる。

```sh
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e13-c1-1.txt ./target/release/e00-serial-probe <PORT> khi
E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e13-c1-2.txt ./target/release/e00-serial-probe <PORT> khi
```

それぞれ約 20 秒かかる。`khi` の後 10 秒待ってから、道具が `d` を送って終わる。

### C-2. `khi` の 1 秒後に `d` を送る（2回）

```sh
E00_WAIT_MS=1000 E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e13-c2-1.txt ./target/release/e00-serial-probe <PORT> khi d
E00_WAIT_MS=1000 E00_FINAL_WAIT_MS=10000 E00_LOG=experimentals/raw/e13-c2-2.txt ./target/release/e00-serial-probe <PORT> khi d
```

`khi` の 1 秒後に `d` をトークンとして送る。その 10 秒後（`khi` から 11 秒後）に、道具が終わるときの `d` をもう一度送る。

### C-3. `khi` の後に `d` を2回続けて送る（1回）

```sh
E00_WAIT_MS=1000 E00_FINAL_WAIT_MS=8000 E00_LOG=experimentals/raw/e13-c3.txt ./target/release/e00-serial-probe <PORT> khi d d
```

`khi` の 1 秒後に1つ目の `d`、その 1 秒後に2つ目の `d` を送る（`E00_WAIT_MS` はトークンの間すべてに掛かる）。その 8 秒後に、道具が3つ目の `d` を送る。

- 最初の `->` より後に `* Start *` が出たら（`d` を重ねて送った後の再起動かもしれない）、その回を捨てずに記録する。P-5 を通してから1回だけやり直し（ファイル名に `-r2`）、その結果も記録する。

## 記録すること

- [ ] P-5 と C-1〜C-3 の出力（`experimentals/raw/` のファイルの中身を、伏せた上で貼る）。やり直した回も、やり直す前の回の出力と一緒に貼る
- [ ] ターミナルに出たが、ファイルには入らない英文の表示（`!! STOP TOKEN NOT SENT`、`the watchdog sent the stop token`、`interrupted` を含む行など）。出なければ「無し」
- [ ] 道具が終わった後もサーボが動いていて電源を切った回があれば、そのこと
- [ ] 道具が終わったときに Bittle が倒れていた回、2m の範囲から出そうで電源を切った回（回の名前、例: `e13-c2-1`）。無ければ「無し」

## 判定基準

使った回だけで判定する。

- C-1 の「3 秒」は、`d` を `khi` の 1 秒後に送ったときに、まだ動作の途中であることを確かめるための下限（設計の選択）。「0.5 秒」は、脚なしの F-B11 のばらつき（約 20 ms）を大きめにとった値で、脚付きでも足りるかは**未確認**（設計の選択）。
- 「`khi` の範囲」は、C-1 の2回の `k` の時刻のうち、小さい方から 0.5 秒引いた時刻から、大きい方に 0.5 秒足した時刻まで（`khi` の `->` から測る）。
- 「`k` が返らない」は、C-2 で、`khi` の `->` からログの最後の行までの間に、`k\r\n` が1つも届いていないこと。
- 「`d` のすぐ後」は、`d` の `->` から 1 秒以内。この 1 秒と、「停止の応答」の 1 秒は、設計案として選んだ値で、脚付きで測っていない。脚付きで休む姿勢へ動くのに時間がかかり、1 秒を超えたら、「分からなかった」（保留）になる。
- 「停止の応答」は、トークンとして送った `d` の `->` から 1 秒以内で、かつ次の `->`（道具が終わるときの `d` を含む）より前に届いた中身（先頭の `khi` の `k\r\n` は除く）をつないだものに、`d\r\n` があり、`?` が無いもの（ソースの `T_REST` の経路では `g\r\nd\r\n` を返す見込み。推論）。`d` が届いた後の受信だけで動作が打ち切られることもあるので（`perform()` は何か届けばやめる見込み）、`k` が無いことと応答が早いことだけでは、`d` の停止の処理が走ったとは言えない。そのため、停止の応答があることを判定の条件にする。

#### 気づいたこと

- B-1 の対照は、答える時点が `d` の後になる組み方だった。道具は問いの約 1.5 秒後に `d` を送り、答えを促す表示はその後に出る（出力の `-> "d"` と `>>> answer` の順）。B-1a-1 の `n` も B-1a-2 の `y` も、`d` の後に入力された。
- B-1a-2 で、問いが出た時点（`kwkF` の約 1 秒後）では動いていて、答えるまでの間に止まったのなら、止まったのが `kwkF` が自分で止まったからなのか、約 2.5 秒後に送った `d` によるのかは、見分けられない（**未確認**）。1回目は `n` と答えた（入力は問いの約 4 秒後、`d` の約 2.5 秒後）。F-B14 では、`kwkF` を1回送っただけで 5 秒後には止まっていた。
- `kwkF` の `k` は、送ってから約 0.37 秒で返った（2回とも。F-B11 と同じ傾向）。B-1a-2 では、その後の問いの時点でも動いていたと答えている（1回、答えは「ようだ」）。`k` は、歩き方では「受け付けた」しるしで、動作の終わりではないと読める（06 2.1節の推論と合う。**未確認**）。`k` が動作の終わりを表すかは、どの動作についても確かめていない。
- 人が答えるまでに時間がかかると、見ている間に状態が変わる（B-1a-2 では、答えを促す表示から答えまで約 49 秒、問いの表示からは約 51 秒）。問いは「そのときの状態」を聞くが、人はその後の様子も見てしまう。
- 道具の動き: 2回とも、問い（`?? …`）は `kwkF` の約 1 秒後に出て、`d` は問いの約 1.5 秒後に送られた。`d` には `\n\r\n` が返った（E00 と同じ）。道具の動作で手順書と違う点は無かった。
