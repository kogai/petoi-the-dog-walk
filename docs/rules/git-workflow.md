# Git の運用

## 1. ブランチ

- `main` に直接コミットしない。
- ブランチ名: `<種類>/<短い説明>`（例: `feat/arbiter`、`docs/transport`、`exp/e00-connectivity`）。
  エージェントのセッションで名前が指定されている場合は、それに従う。

## 2. コミット

- 1コミット1つの目的。件名は英語の命令形で 72 文字以内（例: `Add arbiter with priority rules`）。
- 本文に「なぜ」を書く。関係する設計 ID（D-03 など）や実験 ID（E00 など）があれば書く。
- コミットの前に `mise run check` を通す。

## 3. PR

- **1つの PR で行うことは1つにする。** 理由: レビューの精度が上がる、実装の精度が上がる、あとから読み返し・取り消し・やり直しがしやすい。
  - 例: 設計書の追加、開発ルールの追加、ハーネスの追加、実験1つの依頼、機能1つの実装は、それぞれ別の PR にする。
  - 「ついでの修正」は入れない。見つけたら別の PR にするか、メモに残す。
  - 迷ったら、PR の説明を1文で書けるかで判断する。「〜と〜をする」になるなら分ける。
- 前の PR に依存する PR は、前の PR のブランチを土台にして出す（積み重ねる）。本文に「〜の後にマージする」と書く。
- 本文は `.github/pull_request_template.md` に沿って書く。
- CI が赤い PR はレビューを依頼しない。マージの条件は [review.md](review.md) 1節。

## 4. 実験依頼の流れ

実機・API キー・人の目が要る確認は、エージェントが実行しない。次の流れで人に依頼する。

1. エージェントが `experimentals/E<番号>-<名前>.md` に手順書を作り、**実験1つにつき1つの PR** を出す。
   PR のタイトルは `[実験依頼] E<番号> <名前>`。実験の ID は [07-roadmap.md](../design/07-roadmap.md) の一覧に従う。
2. 依頼の PR は、ほかの PR と同じ条件（[review.md](review.md) 1節）でマージしてよい。マージされた時点で手順書の状態は「依頼中」。
3. 人が手順どおりに実験し、結果を送る。送り方は次のどちらか。
   - 手順書の「結果」節を埋める PR を出す（タイトルは `[実験結果] E<番号> <名前>`）
   - 依頼の PR か issue のコメントに貼る。エージェントが `[実験結果]` の PR を作って、手順書の「結果」節に転記する（記録をリポジトリに残すため）
4. エージェントが結果を読み、`docs/design/`（`facts.md` の事実、`decisions.md` の決定）へ反映する。反映は結果の PR とは別の PR にする（1つの PR で1つのこと）。

実験結果は、記録されるまで「未確認」のまま扱う。
