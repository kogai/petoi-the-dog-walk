# 文書の書き方

## 1. 3種類の区別

| 種類 | 意味 | 書き方 |
|---|---|---|
| 確認済み | 公式ドキュメントまたはコードを読んで確認した事実、または記録済みの実験結果 | `docs/design/facts.md` に ID を付けて置く。出典（URL か、結果が記録された実験 ID）必須 |
| 設計案 | この計画での決め事（実装前・未実行） | 設計書の本文。確定したら `decisions.md` に記録 |
| 未確認 / 実験 | 実機や API で試して確かめる項目 | 実験 ID（E00 など）を付ける |

- 推測を「確認済み」と書かない。読んでいない出典を挙げない。
- 公式ではない出典（第三者のコードなど）から得た事実は、そのことを本文に明記する（二次情報）。二次情報だけを根拠にした決定は「仮決定」にする。
- 実行していないコードには「未実行」と書く。
- 実験の結果が出たら、`facts.md` に事実として足し、出典に実験 ID を書く。

## 2. 文体

- 日本語。「だ・である」調。1文を短く。
- 1つの事実・決めごとは1か所だけに書き、他からは ID かリンクで参照する。
- コード・トークン・ファイル名はバッククォートで囲む。

## 3. 設計とコードの同期

- クレート構成や境界の trait・型を変えたら、同じ PR で [02-architecture.md](../design/02-architecture.md) を直す。
- 未決定事項を決めたら、`decisions.md` の状態・理由・日付を更新する。
- 作業した環境の一時的な事情（ネットワークの制限など）は設計書に書かない。PR の本文に書く。
