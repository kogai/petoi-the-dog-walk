# 06. Bittle との通信

## 1. 確認済み

- ボーレート 115200（F-B4）。
- Wi-Fi（ESP8266）の公式サンプルは `http://<IP>/action?name=<動作名>` を受ける（F-B5）。
- 公式の Python API に `sendSkillStr()`、`autoConnect()` がある（F-B6）。このプロジェクトでは使わない（D-08）。
- シリアル（USB）で実機に送ったときの振る舞い（E00。条件は facts.md の「Bittle の実機」節）:
  - ポートを開くたびに起動の表示が出て、`Ready!` まで約 5.5 秒かかる。それより前に送ると崩れることがある（F-B9）。
  - `k` で始まるトークンには `k` が返る。返るまでの時間はトークンで違う（`kwkF` 約 0.4 秒、`khi` 約 5.5 秒。F-B11）。
  - 知らないトークンには `?<名前>` が返る。改行は LF で通り、CRLF では通らない（F-B12）。
  - 同じトークンを続けて送ったときの扱いは、出力からは決められなかった（F-B13）。
  - `kwkF` を1回送っただけでは、5 秒後には動いていなかった（脚なし、1回。F-B14）。
  - `serialport` クレートで macOS の USB シリアルを扱えた（F-B16）。

## 2. 設計案

`Transport` trait（[02](02-architecture.md)）の実装を3つ用意する。

| 実装 | 用途 | 依存 |
|---|---|---|
| `FakeTransport` | テスト。送ったトークンを記録し、2.1節の応答を返す | なし（`walk-testing`） |
| `SerialTransport` | USB / Bluetooth。シリアルポートにトークンを書き込む | `serialport` クレート（`walk-bittle`） |
| `HttpTransport` | Wi-Fi。`/action?name=` に GET する | HTTP クライアント（`walk-bittle`） |

共通の決まり:

- 送れるのは `Token` 型の値だけ。`Token` は許可リスト（F-T1 の表のうち `walk-core` で使うもの）からしか作れない（[02](02-architecture.md) 3節）。
- 歩き方以外の同じトークンは、続けて送らない（抑止する）。続けて送ったときの扱いが分からなかったので、安全側に倒す（F-B13）。
- 歩き方のトークン（`kwkF` など）は、歩かせている間、一定の間隔で送り直す（F-B14）。間隔の値と、送り直しても歩行が途切れないかは**未確認**（3節）。
- 送信間隔の下限を設ける。既定値は**未定**（E00 では決めなかった。F-B11 の値を参考に、実装の PR で仮の値を置き、実験で見直す）。
- 接続を閉じる前に必ず停止トークン `d` を送る。`Drop` でも送る。`d` で止まるかは**未確認**（3節）。
- Mac 側に非常停止キーを用意する（押すと `d` を送ってループを抜ける）。

### 2.1 `SerialTransport` の振る舞い（設計案。E00 の結果による）

- 改行は LF に固定する（F-B12。設定にしない）。
- 開いた後は、`Ready!` を受け取るまで送らない。`Ready!` が上限の時間（例: 10 秒）までに来なければ、`Err` を返す（F-B9）。
- `send` は、送った後に `k` か `?<名前>` を待つ。
  - `k` を受け取ったら `Ok`。
  - `?<名前>` を受け取ったら `Err`（知らないトークン。`Token` の許可リストがあるので、通常は起きない。ファームとの食い違いを見つけるため）。
  - 待つ時間の上限は、トークンごとに決める。`k` は動作を終えたときに返ると読める（歩き方は受け付けたときに返る）ので、`khi` のように長い動作では、上限を F-B11 の値より長くする。上限を過ぎたら `Err`。
  - 受け取ったものは塊に分かれて届くので、塊をつないでから `k\r\n` と `?<名前>` を探す。
- `Low power` を受け取ったら、上の層に知らせる（F-B15。知らせ方は未定）。
- `FakeTransport` は、上の `k`・`?<名前>`・時間切れを返せるようにして、`walk-app` のテストに使う。

（推論）`k` の意味（「動作を終えた」か）は、F-B11 の時間の差から読んだもので、ファームのコードでは確かめていない。

## 3. 未確認・実験

- `d` で止まるか、止まるまでの遅れ。E00 では確かめなかった。今の道具は問いを出してから `d` を送るので、`d` の後の様子を問えない。道具を直してから、別の実験で確かめる（実験 ID は未定）。
- 歩き方のトークンを送り直す間隔と、送り直しても歩行が途切れないか。脚を付けた状態でも、`kwkF` が止まるか（F-B14 は脚なし）。別の実験で確かめる（実験 ID は未定）。
- Wi-Fi 経路の応答（本文・ステータス・所要時間）。E00 から外した。E04 に含めるか、新しい ID にするかは、その依頼の PR で決める。
- E04: Wi-Fi 経由で、決まった動作名以外（関節の直接指定など）を送れるか。
- `serialport` クレートが Mac の Bluetooth シリアルポートで問題なく動くか（F-B16 は USB だけ）。
