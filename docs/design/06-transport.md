# 06. Bittle との通信

## 1. 確認済み

- ボーレート 115200（F-B4）。
- Wi-Fi（ESP8266）の公式サンプルは `http://<IP>/action?name=<動作名>` を受ける（F-B5）。
- 公式の Python API に `sendSkillStr()`、`autoConnect()` がある（F-B6）。このプロジェクトでは使わない（D-08）。
- シリアル（USB）で実機に送ったときの振る舞い（E00。数値と条件は facts.md の「Bittle の実機」節）:
  - ポートを開くたびに起動の表示が出る。`Ready!` の後、ファームが自分で `g` と `d` を出す。`Ready!` より前に送ると崩れることがある（F-B9）。途中で再起動すると、`Ready!` はさらに遅れる（F-B15）。
  - `k` で始まるトークンには `k` が返る。返るまでの時間はトークンで大きく違う（F-B11）。
  - 知らないトークンには `?<名前>` が返り、その後に `k` も返る。改行は LF で通り、CRLF では知らないトークンとして返る（F-B12）。
  - 同じトークンを続けて送ったときの扱いは、出力からは決められなかった（F-B13）。
  - `kwkF` を1回送っただけでは、5 秒後には動いていなかった（脚なし、1回。F-B14）。
  - `serialport` クレートで macOS の USB シリアルを扱えた（F-B16）。

## 2. 設計案

`Transport` trait（[02](02-architecture.md)）の実装を3つ用意する。

| 実装 | 用途 | 依存 |
|---|---|---|
| `FakeTransport` | テスト。送ったトークンを記録する。`send` が `Ok` か `Err`（知らないトークン、時間切れ）を返すよう設定できる | なし（`walk-testing`） |
| `SerialTransport` | USB / Bluetooth。シリアルポートにトークンを書き込む | `serialport` クレート（`walk-bittle`） |
| `HttpTransport` | Wi-Fi。`/action?name=` に GET する | HTTP クライアント（`walk-bittle`） |

共通の決まり:

- 送れるのは `Token` 型の値だけ。`Token` は許可リスト（F-T1 の表のうち `walk-core` で使うもの）からしか作れない（[02](02-architecture.md) 3節）。
- 歩き方以外の同じトークンは、続けて送らない（抑止する）。続けて送ったときの扱いが分からなかったので、安全側に倒す（F-B13）。
- 歩き方のトークン（`kwkF` など）は、歩かせている間、一定の間隔で送り直す（F-B14）。間隔の値と、送り直しても歩行が途切れないかは**未確認**（E14）。
- 送信間隔の下限を設ける。既定値は**未定**（E00 では決めなかった。実装の PR で仮の値を置き、実験で見直す）。
- 接続を閉じる前に必ず停止トークン `d` を送る。`Drop` でも送る。`d` で止まるかは**未確認**（E13）。
- Mac 側に非常停止キーを用意する（押すと `d` を送ってループを抜ける）。

### 2.1 `SerialTransport` の振る舞い（設計案。E00 の結果による）

- 改行は LF に固定する（F-B12。設定にしない）。
- 開いた後は、`Ready!` を受け取るまで送らない。`Ready!` の後、決めた時間（例: 1.5 秒）待ち、それまでに受け取ったもの（起動の表示の先頭の `k`、ファームが自分で出す `g`・`d`）を捨ててから送る。捨てる前に `Low power` が含まれていないかを見て、あれば上の層に知らせる（下の `Low power` の項）。`g`・`d` は来なくてもよい（途中で再起動したときは出なかった。F-B9、F-B15）。
- 待っている間に `* Start *` を2回受け取ったら（途中で再起動した）、`Err` にして上の層に知らせる（F-B15。推論: 電池の不足が疑われる）。`Ready!` を待つ上限は、再起動が無い場合に足りる値（例: 8 秒。F-B9 は約 5.5 秒）にし、上限までに来なければ `Err`。
- 送った後は、受け取った塊をつないで、`k\r\n` を探す。
  - `k\r\n` より前に `?<名前>` が届いていたら `Err`（知らないトークン）。知らないトークンにも `k` が続くので（F-B12）、受け取った順を見る。`Token` の許可リストがあるので通常は起きないが、ファームとの食い違いを見つけるために扱う。
  - `?<名前>` 無しで `k\r\n` を受け取ったら `Ok`。
  - 待つ時間の上限は、トークンごとに決める。`khi` のように長い動作では、上限を F-B11 の値より長くする。上限を過ぎたら `Err`（時間切れ）。時間切れのときは、同じトークンを送り直さない（[02](02-architecture.md) 5節の再試行は、書き込みの失敗だけに使う）。
  - `k` を待つ間、ループ（100ms 周期、[02](02-architecture.md) 4節）と非常停止を止めない。そのための形（送信を別スレッドに置く、`send` は書くだけにして応答を別に読む、など）は D-15 で決める。
- `Low power` を受け取ったら、上の層に知らせる（F-B15）。知らせ方は**未定**（3節）。

（推論）`k` は「動作を終えた（歩き方は受け付けた）」しるしと読める。F-B11 の時間の差から読んだもので、ファームのコードでは確かめていない。

### 2.2 `FakeTransport` と記録済みの応答

- `walk-app` のテストでは、`FakeTransport` の `send` が `Ok`・`Err`（知らないトークン、時間切れ）を返すよう設定して使う。
- `SerialTransport` の受信の解釈（`Ready!` を待つ、`k\r\n` と `?<名前>` を探す）は、E00 で記録した出力を入力にしてテストする（[testing.md](../rules/testing.md) の契約テスト）。

## 3. 未確認・実験・未決定

- E13: `d` で止まるか、止まるまでの遅れ。E00 では確かめなかった。今の道具は問いを出してから `d` を送るので、`d` の後の様子を問えない。道具を直してから依頼する。
- E14: 歩き方のトークンを送り直す間隔と、送り直しても歩行が途切れないか。脚を付けた状態でも、`kwkF` を1回送っただけで止まるか（F-B14 は脚なし）。
- `Ready!` の直後（ファームが自分で `g`・`d` を出す前）に送ったときの振る舞い。途中で再起動した後、何も送らなければ `g`・`d` が出るか。2.1節では決めた時間だけ待ち、再起動は `Err` にするので、確かめなくても進められる。
- E15: Wi-Fi 経路の応答（本文・ステータス・所要時間）。E00 から外した。
- E04: Wi-Fi 経由で、決まった動作名以外（関節の直接指定など）を送れるか。
- `serialport` クレートが Mac の Bluetooth シリアルポートで問題なく動くか（F-B16 は USB だけ）。
- 未決定: `k` を待つ間にループを止めない形（D-15）。`Low power` を上の層に知らせる方法（今の `Transport` trait には口が無い。D-15 と合わせて決める）。
