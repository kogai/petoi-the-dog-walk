# 07. ロードマップ（設計案）

| フェーズ | 内容 | 完了条件 | 待つ実験 |
|---|---|---|---|
| 0 | 設計書、開発ルール、ハーネス（テスト・静的検査・CI・レビュー体制） | 検査が CI で通る。ルールが揃う | なし |
| 1a | `walk-core`（型・調停・スキル）と、`walk-app` の文章の読み込みを実装 | 単体・プロパティテストが通る | なし |
| 1b | `walk-jev`（記録済み応答で）と、`walk-app` のループを Fake で結合 | Fake 一式でループが決定的に回る | E05（英訳の要否） |
| 1c | `walk-bittle` の本物の送信をつなぐ | 実機で指示どおりに座る・歩く・止まる | E00 |
| 2 | 実験結果を反映し、センサーの読み取りを足す | 状況（`situation`）に実センサーが入る | E01, E02, E04, E06, E07 |
| 3 | 反射層（`walk-flybrain`）を足す | 反射層の有無で振る舞いが変わる | E08, D-06 |

- フェーズ 1a は実験を待たずに進められる。
- 本物の Jev を初めて呼ぶのは E05（人が実行する）。本体から呼ぶのは 1b の終わりで、`walk-jev` の実 API テストを人が手元で実行する。
- 実機を動かす確認（1c 以降）は人が実行し、結果を実験の記録に残す。
- 1つの PR では1つのことだけを行う（設計・ルール・ハーネス・各実験の依頼を別々の PR にする）。

## 実験の一覧（設計案）

[計画書](https://github.com/kogai/petoi-the-dog-walk/blob/5174b74/README.md)の「6. 実験項目」に ID を付けたもの。手順書は、依頼するときに実験ごとの PR で作る。

| ID | 内容 | 計画書の項目 | 待っている設計 |

| E00 | トークンを送ったときの応答の形式（エコー・時間・連続送信・歩行の継続） | （新規） | 06、`SerialTransport` |
| E01 | 標準ファームのまま、PC から IMU の値を読み出せるか | 1 | D-01、D-02 |
| E02 | カメラの認識結果を Mac へ渡せるか | 2 | D-02 |
| E04 | Wi-Fi 経由で、決まった動作名以外を送れるか | 4 | 06、`HttpTransport` |
| E05 | 日本語の性格文が Jev にどこまで効くか（英訳との比較）。F-J9 の呼び方で呼べるか。指示あり・なしの2つの Choice が区別されるか | 5 | D-04、D-10、D-11 |
| E06 | Grove G2（A2/A3、F-B3）のアナログ値を、標準ファームのシリアルコマンドで読めるか（計画書では公式 Python API の `readAnalogValue(pin)` で確かめる予定だった。D-08 で Python API は使わない） | 6 | D-02 |
| E07 | 複数の拡張モジュールを1つのファームで使えるか | 7 | D-02 |

- E03 は欠番。計画書の項目3「反射で反応させる対象を決める」は実験ではなく決定なので、D-02 にした。
