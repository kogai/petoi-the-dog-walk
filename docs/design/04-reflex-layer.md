# 04. 反射層（ハエ脳）

フェーズ3で足す。フェーズ1・2では、常に「何もしない」を返す `Reflex` の実装（`walk-core` に置く）を使う（G4）。

## 1. 役割（設計案）

100ms ごとに速い反応を出す。判断の中心ではない。

## 2. 出力の対応（設計案）

ハエ脳の出力は7種類（F-F8）。

| ハエの動き（運動ニューロン群） | Bittle |
|---|---|
| stand（どの群も閾値未満） | `kbalance`（または `kup`） |
| walk_forward（fwd） | `kwkF` |
| walk_backward（back） | `kbk` |
| jump_away（jump） | 対応スキル未確認（代替案: `kbk` か `krnF`）→ D-07 |
| punch（punch）/ kick（kick）/ block（wing） | 対応する動作が確認できていない → D-07 |

## 3. 感覚入力（未確認）

公式実装の感覚入力はゲーム状態から作られている（F-F4）。Bittle で何を入力にするかは、
E01（IMU）・E02（カメラ）・E16（持ち上げ）の結果で選べる範囲が決まる（D-02）。

## 4. 性格づけ（設計案）

Jev の答え（Score や Noul）を、群ごとの閾値・ゲイン（F-F3）の倍率にコード側で変換する。
例: 臆病さが高いと、後退・逃避の閾値を下げる。
変換は純粋関数にして単体テストする。実機で違いが見えるかは E08。

## 5. 実行方法（未決定 D-06）

公式実装のシミュレーションはブラウザの JavaScript で動き、`server.py` は配信・Jev の中継・記録だけを行う（F-F1、F-F9）。
そのため `server.py` を別のプログラムから呼んでも、シミュレーションは使えない。選択肢:

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 公式の JavaScript を Node.js の子プロセスで動かし、標準入出力でつなぐ | 公式と同じコードを使える | シミュレーションの本体はブラウザの API を使っていない（F-F12）が、Node から呼ぶ入口（`flyworker.js` の代わり）を新しく書く必要がある。プロセス間の遅延と、JS 側の型の無さが残る |
| B | Rust へ移植する | 型が付き、1プロセスで動き、テストしやすい。1.2万ニューロン・100ms 周期でも性能は足りる見込み（未確認） | 移植の正しさの検証が必要 |
| C | ブラウザで動かし、WebSocket でつなぐ | 可視化がそのまま使える | 自動テストが難しい |

本体を Rust にした（D-09）ので、案 B が第一候補になる。
移植の正しさは、比べる相手で同じ入力（感覚入力の列と乱数の種）を与えたときの出力を記録し、
Rust 版の出力と比べるテスト（ゴールデンテスト）で確かめる。
公式の JavaScript は乱数の種を指定でき、シミュレーションの本体（`flybrain.js`）はブラウザの API を使っていない（F-F12）。

`flybrain.js` は冒頭のコメントで Shiu et al. の `model.py` の移植としているが、式もパラメーターも違う（F-F11、F-F15）。
そのため、比べる相手を選ぶ必要がある（D-06 と一緒に決める）。

| 相手 | 利点 | 欠点 |
|---|---|---|
| `mk-jev-fly-brain` の `flybrain.js` と部分回路（F-F11〜F-F13） | 種を合わせて、出力を1対1で比べられる見込み（Rust と JS で浮動小数の計算の順を揃えられるかは未確認）。部分回路と、運動の群の読み出しが揃っている | 生理のパラメーターは作者の仮定（F-F11）。移植元とされる `src/model.py` はリポジトリに無い（F-F11） |
| Shiu et al. の `model.py`（F-F14、F-F15） | 論文で使われたモデル。移植版を Brian 2 版と比べた先例がある（F-F16） | 脳全体のままでは、Brian 2 の CPU 版でも実時間より遅い（F-F16。第三者の測定）。100ms 周期で使うには部分回路を作る必要がある見込み（F-F16 は第三者の測定で、機械は不明）。Brian 2 の乱数の列を Rust で再現するのは難しい見込みで（未確認）、比べるのは分布になる見込み |

ライセンス（設計案）: このリポジトリは MIT（`Cargo.toml` の `license`）。
- `mk-jev-fly-brain` のコードと Shiu et al. の `model.py` は MIT（F-F13、F-F14）なので、著作権表示と許諾文（元の MIT ライセンスの本文）を残せば、参照して移植してよい。
- 部分回路 `fly_circuit.js` は CC-BY 4.0（F-F13）なので、使うなら帰属表示を付ける。
- Shiu et al. のリポジトリの配線データ（FlyWire 由来）のライセンスは未確認。
- `eonsystemspbc/fly-brain` は GPL-2.0（F-F16）なので、コードは写さず、比べ方を参考にするだけにする。

未確認（E17）: Node で `flybrain.js` を動かしたとき、同じ種で同じ出力になるか。100ms 分の計算にかかる時間。
実機も API キーも要らないので、人への依頼ではなく、エージェントが実行して記録する。

どの案でも `Reflex` trait の後ろに隠すので、他のクレートには影響しない。

## 6. 機体に積む案（未決定 D-18）

反射層は本能・反射なので、Mac から離れても機体だけで動くと望ましい。その実現の方法を検討する。

NyBoard のマイコンには載らない（F-B1）。必要な量の見積もり（設計案。ニューロン数・結合数・刻みは F-F11、F-F13。それ以外は仮定）:

- 動いている間の状態: 1ニューロンに4値（電位、興奮と抑制のコンダクタンス、不応期と仮定）× 4バイト（f32 と仮定）で、1.2万ニューロンで約190KB。SRAM 2KB の約100倍。1値 × 1バイトに詰めても 12KB で、2KB を超える
- 配線: 1結合1バイトに詰めても約0.94MB で、Flash 32KB の約29倍
- 計算: 刻み 0.25ms なので、100ms 分で 400 ステップ。1.2万ニューロン分で、100ms ごとに約480万回の更新。16MHz（F-B1）では 100ms に 160万サイクルしかなく、1回の更新に1サイクルも使えない（結合を伝える計算は含めていない）

仮に SD カードに配線を置けても（NyBoard で使えるかは未確認）、状態の置き場所と計算の速さは変わらないので、NyBoard のままでは足りない見込み。

候補（どれも未確認）:

| 案 | 内容 | 未確認の点 |
|---|---|---|
| Raspberry Pi を積む | OpenCat は Raspberry Pi をつなぐ形を想定している（F-B20）。Pi で Rust の同じコードを動かし、NyBoard へはシリアルで送る | 手元の Pi の型。つなぎ方・電源・背中のカバーとの干渉（公式の手順は D-18 の材料）。100ms 周期に間に合うか（E17 の値から見積もり、必要ならボードの上で測る） |
| BiBoard（ESP32）に差し替える | Bittle X などの現行の製品のボード（F-B20）。ファームは別のリポジトリ | 初代 Bittle に取り付けられるか（サーボのコネクター・固定・電源）。計算が間に合うか。回路を小さくする必要があるか。ファームが変わるので、F-B 系の事実と `walk-bittle` の前提も変わる |

どちらの案でも、判断のロジックは `walk-core` に `#![no_std]` の純粋関数で書くので（[02](02-architecture.md)）、動かす場所が変わっても書き直さずに済む見込み。
Pi から NyBoard へのつなぎ方は、`Link` の実装の1つとして足すか、シリアルの `SerialLink`（ADR-0001 の例）をそのまま使う形になる見込み（[ADR-0001](adr/0001-driver-layer.md)）。

反射層だけをボードに置き、Mac も NyBoard へ送る形にすると、NyBoard に書く者が2つになる。
そのとき調停（[05](05-arbitration.md)）をどこで行うか、停止がどちらの送信も追い越せるか（ADR-0001 2.6節）が新しい論点になる（D-18 の論点 (b)）。
