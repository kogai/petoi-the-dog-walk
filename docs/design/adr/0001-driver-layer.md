# ADR-0001: デバイスと外部 API をドライバー層で抽象化する

- 状態: 決定（2026-10-16。[D-16](../decisions.md)）
- 決めた人: オーナーの指示（「アーキテクチャ図はそのままで、センサーやデバイス、API などはドライバー層を作って抽象化して、テストで差し替え可能・デバイス自体を差し替え可能な構造にしたい」）
- 関係する文書: [02](../02-architecture.md)（クレートの分け方・境界の trait）、[06](../06-transport.md)（`SerialTransport`）、[docs/rules/testing.md](../../rules/testing.md)

この ADR の中身は **設計案**（実装前・未実行）。決まったのは「この構造にする」という方針で、trait の細部は実装の PR で決める。

## 1. 背景

- [02](../02-architecture.md) 3節では、`walk-core` に境界の trait（`Transport`、`Reasoner`、`Reflex`）を置き、殻のクレートが実装する。この形は変えない。
- E00 の結果、Bittle との通信には、トークンを書くだけでなく、起動の `Ready!` を待つ、`k` や `?<名前>` を待つ、受け取った塊をつなぐ、といった手順が要ると分かった（[06](../06-transport.md) 2.1節、F-B9〜F-B12）。今の構成では、この手順はシリアルポートを直接持つ `SerialTransport` の中に入るので、**実機が無いとテストできない**。
- これから足すもの（IMU などのセンサー、カメラ、Wi-Fi、Bluetooth）も、同じように「デバイスとのやり取りの手順」と「バイトの通り道」が混ざりやすい。
- 将来、Bittle 以外のロボットや別のセンサーに替える余地を残したい（オーナーの方針）。

## 2. 決定

アーキテクチャ図（[02](../02-architecture.md) 1節）は変えない。図の `sensing`・`reasoner`・`reflex`・`transport` の各箱の中を、次の3段に分ける。

```
 walk-app（組み立て）  設定を読んで、どのドライバーを使うかを選び、trait として渡す
      │
      ▼
 境界の trait（walk-core）   Transport / Reasoner / Reflex / センサーの trait / Clock / Link
      ▲ 実装する
      │
 ドライバー（殻のクレート）  デバイスや API ごとに1つ。手順（プロトコル）だけを持つ
      │ 使う
      ▼
 リンク（Link の実装）       バイトの通り道。シリアル（USB・Bluetooth）など。中身を知らない
```

### 2.1 境界の trait（`walk-core`）

- 上の層が使う「デバイスの役目」の trait を置く（今ある `Transport`・`Reasoner`・`Reflex` に加えて、センサーの trait）。上の層（`walk-app` のループ、調停）は、この trait だけを見て、どのデバイスかを知らない。
- センサーの trait は、何を読めるかが E01・E02 で決まってから足す（例: IMU の値を返す trait）。名前と形は未定。
- 新しく **`Link`**（バイトを書く・時間の上限付きで読む）と **`Clock`**（今の `Millis` を返す）の trait を置く。どちらも `#![no_std]` のまま書ける形にする（`std::io` を使わない）。
- trait には「契約」（守るべき振る舞い。例: `Link` の読み取りは、上限の時間を過ぎたら何も読まずに返る）を doc コメントで書く。

### 2.2 ドライバー（殻のクレート）

- デバイスや API ごとに1つのドライバーを置く（例: Bittle のドライバーは `walk-bittle`、Jev は `walk-jev`、ハエ脳は `walk-flybrain`）。クレートの数と名前は今の [02](../02-architecture.md) 2節のまま。
- ドライバーは、デバイスとのやり取りの**手順**（起動を待つ、応答を待つ、塊をつなぐ、エラーの応答を見分ける）だけを持つ。判断のロジックは持たない（判断は `walk-core` の純粋関数）。
- ドライバーは `Link` と `Clock` を引数で受け取り、ジェネリクスで持つ（例: `BittleSerial<L: Link, C: Clock>`）。シリアルポートや HTTP クライアントを直接は持たない。
- 手順のうち、受け取ったバイトの解釈（`k\r\n` や `?<名前>` を探す、など）は、純粋関数にして、ドライバーの中か `walk-core` に置く。どちらに置くかは実装の PR で決める。
- 1つのデバイスが複数の役目を持つとき（例: Bittle は動作の送信と IMU の読み取りを同じシリアルで行う見込み。E01 で確かめる）、1つのドライバーが1つの `Link` を持ち、複数の trait を実装する。ポートを二重に開かない。
- 応答を待つ間にループを止めない形（[D-15](../decisions.md)）は、この ADR では決めない。ドライバーが受信用のスレッドを持ち、受け取ったものを上の層へ渡す案は、この構造と両立する（設計案）。

### 2.3 リンク（`Link` の実装）

- バイトの流れで話す通り道（シリアル。USB と Bluetooth のどちらも、Mac ではシリアルポートとして扱う見込み。Bluetooth は未確認）ごとに、`Link` を実装する小さな型を置く（例: `serialport` を包む `SerialLink`）。置き場所は、それを使うドライバーのクレート（今は `walk-bittle`）。
- HTTP のように要求と応答の組で話す通り道は、バイトの流れとは形が違うので `Link` にしない。HTTP 用の別の境界の trait（例: 要求を渡して応答を受け取る `HttpClient`）を置き、Wi-Fi の Bittle のドライバーと Jev のドライバーが使う案がある（設計案）。形は、Wi-Fi の応答を確かめる E15 と、`walk-jev` の実装の PR で決める。
- リンクは中身（トークンや応答の意味）を知らない。

### 2.4 組み立て（`walk-app`）

- 設定（例: `profiles/` か起動時の引数）で、どのドライバーとリンクを使うかを選び、`Box<dyn Transport>` などとしてループに渡す。設定の形は未定（実装の PR で決める）。
- デバイスを替えるときは、新しいドライバーのクレートを足し、`walk-app` の組み立てに1か所足す。上の層は変えない。

### 2.5 テストでの差し替え

| 差し替える所 | 偽物 | 使い方 |
|---|---|---|
| 境界の trait（`Transport` など） | `walk-testing` の Fake（今の方針どおり） | `walk-app` のループや調停のつながりを、実機なしで確かめる |
| `Link` | `walk-testing` の `FakeLink`（決めたバイト列を、決めた時刻に返す） | ドライバーの手順を、実機なしで確かめる。E00 で記録した出力（`experimentals/E00-connectivity.md`）を、そのまま入力にできる |
| `Clock` | `walk-testing` の偽の時計（今の方針どおり） | 時間切れの扱いを、実時間を待たずに確かめる |

- 契約テスト（[testing.md](../../rules/testing.md)）: 同じテストの関数を、Fake と本物のドライバー（`FakeLink` を付けたもの）の両方に通し、Fake が本物とずれないようにする。本物のリンクで動かすテストは、今の方針どおり `live-hardware` を付けたときだけで、人が実行する。

## 3. 理由

- 実機が無くても、デバイスとのやり取りの手順をテストできる。E00 で分かった手順（`Ready!` を待つ、`k` を待つなど）は間違えやすく、ここが壊れると実機が止まらない・動かない、につながる。
- デバイスや通り道を替えても、上の層とテストが変わらない（USB を Bluetooth に替える、Bittle を別のロボットに替える）。
- `Link` と `Clock` を `walk-core` に置けば、クレートを増やさずに済み、依存の境界（`cargo xtask deps` の照合の表）も変えなくてよい。

## 4. 検討して採らなかった案

- **今のまま（ドライバーがシリアルポートを直接持つ）**: 手順のテストに実機が要る。E00 の後では、手順が増えたので採らない。
- **`Link` を別のクレート（例: `walk-link`）に置く**: `std::io` をそのまま使えるが、クレートと依存の境界が増える。`walk-core` に `no_std` で置けるので採らない。置けないと分かったら見直す。
- **どこでも `dyn` を使う**: ドライバーの中はジェネリクスで十分で、実行時に選ぶ必要があるのは `walk-app` の組み立てだけなので、`dyn` はそこだけにする。
- **既存の HAL（例: 組み込み向けの `embedded-hal`）の trait を使う**: マイコン向けの形で、Mac の上のシリアルや HTTP、Jev の API には合わない（推論）。依存も増えるので採らない。

## 5. 影響

- [02](../02-architecture.md): 2.3節「ドライバー層」を足し、2節の表と3節のスケッチ（`Link`・`Clock`）、4節の時計の扱いを直す（この ADR と同じ PR）。
- [06](../06-transport.md): `SerialTransport` は、Bittle のドライバーが `SerialLink` を使う形として読む（この ADR と同じ PR で注記する）。
- `walk-testing` に `FakeLink` を足す（実装の PR）。
- `docs/rules/coding.md`・`testing.md`: 実装の PR で、ドライバーとリンクの書き方を足す。
- `cargo xtask deps` の照合の表: 変えない（クレートを増やさないため）。
