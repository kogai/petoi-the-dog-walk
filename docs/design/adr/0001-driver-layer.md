# ADR-0001: デバイスと外部 API をドライバー層で抽象化する

- 状態: [decisions.md](../decisions.md) の D-16 を見る（状態はあの表だけに書く）。この ADR は、D-16 の詳しい中身と理由を書く。
- きっかけ: オーナーの指示（「アーキテクチャ図はそのままで、センサーやデバイス、API などはドライバー層を作って抽象化して、テストで差し替え可能・デバイス自体を差し替え可能な構造にしたい」）。境界を `Action` にすること（2.1節）は、オーナーが選んだ（2026-10-16）。
- 関係する文書: [02](../02-architecture.md)（クレートの分け方・境界の trait）、[05](../05-arbitration.md)（調停の出力）、[06](../06-transport.md)（`SerialTransport`）、[docs/rules/testing.md](../../rules/testing.md)

この ADR の中身は **設計案**（実装前・未実行）。決まったのは方針（3段に分ける、境界は `Action`、2.6節の安全の不変条件）で、細部は D-17 に未決定として残す。

## 1. 背景

- [02](../02-architecture.md) 3節では、`walk-core` に境界の trait（`Transport`、`Reasoner`、`Reflex`）を置き、殻のクレートが実装する。この形は変えない。
- E00 の結果、Bittle との通信には、トークンを書くだけでなく、起動の `Ready!` を待つ、`k` や `?<名前>` を待つ、受け取った塊をつなぐ、といった手順が要ると分かった（[06](../06-transport.md) 2.1節、F-B9〜F-B12）。今の構成では、この手順はシリアルポートを直接持つ `SerialTransport` の中に入るので、**実機が無いとテストできない**。
- これから足すもの（IMU などのセンサー、カメラ、Wi-Fi、Bluetooth）も、同じように「デバイスとのやり取りの手順」と「バイトの通り道」が混ざりやすい。
- 今の `Transport::send` は Bittle のトークン（`Token`。F-T1 の許可リスト）を受け取り、動作→トークン表も `walk-core` にある。このままでは、Bittle 以外のロボットに替えると `walk-core` とそのテストが変わる。

## 2. 決定

アーキテクチャ図（[02](../02-architecture.md) 1節）は変えない。図の `sensing`・`reasoner`・`reflex`・`transport` の各箱の中を、次の3段に分ける。

```
 walk-app（組み立て）  設定を読んで、どのドライバーを使うかを選び、trait として渡す
      │
      ▼
 境界の trait（walk-core）   Transport / Reasoner / Reflex / センサーの trait / Clock / Link
      ▲ 実装する
      │
 ドライバー（殻のクレート）  デバイスや API ごとに1つ。手順（プロトコル）と、デバイス固有の表を持つ
      │ 使う
      ▼
 リンク（Link の実装）       バイトの流れの通り道。シリアル（USB・Bluetooth）など。中身を知らない
```

### 2.1 境界の trait（`walk-core`）

- 上の層が使う「デバイスの役目」の trait を置く（今ある `Transport`・`Reasoner`・`Reflex` に加えて、センサーの trait）。上の層（`walk-app` のループ、調停）は、この trait だけを見て、どのデバイスかを知らない。
- **動かす指示は、意味（`Action`）で渡す。** `Transport::send` は `Action` を受け取る。`Action` からデバイスのトークンへの変換（動作→トークン表と `Token` 型）は、Bittle のドライバー（`walk-bittle`）に移す。別のロボットに替えるときは、そのロボットのドライバーが自分の表を持つ。
  - 許可リストは2段で守る。上の層が出せるのは `Action` の enum の値だけ。ドライバーが書けるのは、自分の表にあるトークンだけ（2.6節 S5）。
  - スキル（`Command::Skill`）は、`Action` の並びに展開する（[05](../05-arbitration.md) P5）。スキルの形式（D-05 は「トークン列」）は、フェーズ 1a の見直しで `Action` の並びにする方向で決め直す。そのときの条件: 人が書く `skills.toml` の名前は、読み込むときに `Action` の enum に変え、知らない名前があれば起動しない（許可リストの1段目）。
  - ドライバーが対応しない `Action` は必ず `Err` にする（2.6節 S11）。それより先の扱いは D-17 で決める。
- センサーの trait は、何を読めるかが E01・E02 で決まってから足す（例: IMU の値を返す trait）。名前と形は D-17。
- 新しく **`Link`**（バイトを書く・読む。どちらも時間の上限付き）と **`Clock`**（今の時刻 `Millis` を返す。単調に増える）の trait を置く。どちらも `#![no_std]` のまま書ける形にする（`std::io` を使わない。推論: 書けるはず。実装の PR で確かめる）。
- trait には「契約」（守るべき振る舞い。例: `Link` の読み取りは、上限の時間を過ぎたら何も読まずに返る）を doc コメントで書く。

### 2.2 ドライバー（殻のクレート）

- デバイスや API ごとに1つのドライバーを置く（例: Bittle のドライバーは `walk-bittle`、Jev は `walk-jev`、ハエ脳は `walk-flybrain`）。クレートの数と名前は今の [02](../02-architecture.md) 2節のまま。
- ドライバーは、デバイスとのやり取りの**手順**（起動を待つ、応答を待つ、塊をつなぐ、エラーの応答を見分ける）と、デバイス固有の表（`Action`→トークン）だけを持つ。判断のロジックは持たない（判断は `walk-core` の純粋関数）。
- バイトの流れで話すデバイスのドライバーは、`Link` と `Clock` を引数で受け取り、ジェネリクスで持つ（例: `SerialTransport<L: Link, C: Clock>`）。シリアルポートを直接は持たない。HTTP で話すドライバー（Wi-Fi の Bittle、Jev）が何を受け取るかは、2.3節の案が決まるまで未定（D-17）。
- 受け取ったバイトの解釈（`k\r\n` や `?<名前>` を探す、など）は純粋関数にする。ドライバーの中と `walk-core` のどちらに置くかは D-17。
- 1つのデバイスが複数の役目を持つとき（例: Bittle は動作の送信と IMU の読み取りを同じシリアルで行う見込み。E01 で確かめる）、1つのドライバーが1つのデバイスを受け持ち、複数の trait を実装する。ポートを二重に開かない（読み手と書き手に分けることは別。2.6節 S2）。
- 応答を待つ間にループを止めない形（[D-15](../decisions.md)）は、この ADR では決めない。ドライバーが受信用のスレッドを持つ案をとるなら、`Link` を読み手と書き手に分ける形が要る（2.6節 S2・S6）。`Link` の形（分けるか、分け方、`Send` が要るか）は、D-15 と合わせて決める（D-17）。

### 2.3 リンク（`Link` の実装）

- バイトの流れで話す通り道（シリアル。USB と Bluetooth のどちらも、Mac ではシリアルポートとして扱う見込み。Bluetooth は未確認）ごとに、`Link` を実装する小さな型を置く（例: `serialport` を包む `SerialLink`）。置き場所は、それを使うドライバーのクレート（今は `walk-bittle`）。
- HTTP のように要求と応答の組で話す通り道は、バイトの流れとは形が違うので `Link` にしない。HTTP 用の別の境界の trait（例: 要求を渡して応答を受け取る `HttpClient`）を置き、Wi-Fi の Bittle のドライバーと Jev のドライバーが使う案がある（設計案）。形は D-17（決め方: E15 と `walk-jev` の実装）。
- リンクは中身（トークンや応答の意味）を知らない。

### 2.4 組み立て（`walk-app`）

- 設定で、どのドライバーとリンクを使うかを選び、`Box<dyn Transport>` などとしてループに渡す。選べるのは `walk-app` にある enum の値だけ（2.6節 S9）。設定の形（`profiles/` か起動時の引数か）は D-17。
- デバイスを替えるときは、新しいドライバーのクレートを足し、`walk-app` の組み立てに1か所足す。上の層（`walk-core` の調停・ループ）は変えない。

### 2.5 テストでの差し替え

| 差し替える所 | 偽物 | 使い方 |
|---|---|---|
| 境界の trait（`Transport` など） | `walk-testing` の Fake（今の方針どおり。Fake はドライバーではなく、境界の trait の偽物） | `walk-app` のループや調停のつながりを、実機なしで確かめる |
| `Link` | `walk-testing` の `FakeLink`（決めたバイト列を、決めた時刻に返す） | ドライバーの手順を、実機なしで確かめる。E00 で記録した出力（`experimentals/E00-connectivity.md`）を、そのまま入力にできる |
| `Clock` | `walk-testing` の偽の時計（今の方針どおり） | 時間切れの扱いを、実時間を待たずに確かめる |

- `FakeLink` と偽の時計は、同じ時刻を共有させる（`FakeLink` の「決めた時刻」は偽の時計の上の時刻）。`Link` の読み取りの上限を、注入した `Clock` の上で測る契約にするかは D-17。
- 契約テスト（[testing.md](../../rules/testing.md)）: 同じテストの関数を、Fake と本物のドライバー（`FakeLink` を付けたもの）の両方に通し、Fake が本物とずれないようにする。契約テストには、2.6節の安全の不変条件を入れる（例: 本物のドライバーは、`stop` と `Drop` のときに `FakeLink` へ `d\n` を書く。`FakeLink` の書き込みが失敗したら、`stop` は `Err` を返す。`send` の待ちの途中で `stop` すると、`FakeLink` に書かれた最後のバイト列が `d\n` で、その後に何も書かれない。歩き方の送り直しの間隔を過ぎても、`stop` の後は何も書かれない。対応しない `Action` には `Err` を返す）。本物のリンクで動かすテストは、今の方針どおり `live-hardware` を付けたときだけで、人が実行する。

### 2.6 安全の不変条件（[02](../02-architecture.md) 5節と [06](../06-transport.md) 2節を、新しい層に引き継ぐ）

層を分けても、ロボットを止める経路の保証は弱めない。どのドライバーも次を守る（実装の PR で契約テストにする）。

- S1 停止の送信（`stop` と `Drop`。Bittle では `d`）は、ドライバーの責任とする。リンクにも上の層にも置かない（リンクは中身を知らないため）。終了と Ctrl-C の経路では、`walk-app` が `Drop` に任せず、明示して `stop()` を呼ぶ。`Drop` は最後の備えとする。送れなかったら、02 5節のとおり端末にはっきり表示する。
- S2 1つのデバイスが複数の役目を持っても、停止を書く手段は、ほかの役目の寿命や受信の待ちに左右されない。例: リンクを「書き手」と「読み手」に分け（`serialport` の `try_clone` など。E00 の道具は、停止用に2つ目のハンドルを使っている）、書き手はドライバー本体だけが持つ。センサーの役目はリンクを持たず、ドライバーから読み取りの結果を受け取るだけにする。ロックを使う場合でも、ロックが壊れていた（poison）ときに停止を書くのをやめない。
- S3 `stop` は、`send` が応答を待っている途中でも、それを追い越して停止を書ける。D-15 でどの形を選んでも、これを条件とする。停止（`stop`・`Drop`・`Action::Stop`）は、送信間隔の下限と連続送信の抑止の対象にしない（1回目が届いていなくても、2回目を送れるようにする）。
- S4 `Link` の書き込みにも時間の上限を持たせる。上限までに全部書けたら `Ok`、そうでなければ `Err`（途中まで書いた状態を `Ok` にしない）。リンクの中では再試行しない（再試行の方針は、ドライバーが 02 5節に従って持つ）。`SerialLink` は `serialport` の時間の上限を必ず設定する。
- S5 ドライバーがリンクに書くバイトは、自分の表（許可リスト）のトークンと、決めた改行（LF）だけにする。センサーの問い合わせに使うトークンも表に載せる。送信間隔の下限は、役目をまたいで、リンクごとに数える。
- S6 共有したリンクを読むのは、ドライバーの中の1か所だけにし、そこで受け取ったもの（`k`、`?<名前>`、`Low power`、センサーの値）を役目ごとに分ける。ほかの役目が読んで捨てることはしない。分け方の形は、D-15 と E01 の結果に合わせて決める。
- S7 時間の長さと時刻は、型を分ける（例: 時刻は `Millis`、長さは `MillisSpan`）。時刻をそのまま時間の上限に渡す誤りを型で止める。
- S8 HTTP の境界（2.3節の案）も、要求ごとに時間の上限を持ち、時間切れのときは送り直さない。
- S9 `walk-app` が選べるドライバーは、`walk-app` にある enum の値だけにする。設定に知らない値があれば起動しない。
- S10 `stop` が停止を書いた後は、そのドライバーはどの役目からも動かすトークンを書かない。送信中の `send` の再試行、歩き方の送り直し、受け付け済みの送信をすべて取り消して `Err` にする。`stop` の後の `send` は、`Action::Stop` でも、組み立て直すまで `Err` を返す。`stop()` は何度呼んでもよく、呼ぶたびに停止を書く（S3 の「2回目」はこれを指す。明示した `stop` の後の `Drop` も、もう一度書く）。停止と他の書き込みは、1つのトークン（LF まで）の単位で混ざらないようにする。
- S11 ドライバーが対応しない `Action` は必ず `Err` にし、黙って `Ok` にしない（上の層が「変えた」と思ったまま、前の動作が続くのを防ぐ）。すべてのドライバーは `Action::Stop` と `stop()` を必ず受け持ち、どちらも同じ停止（Bittle では `d`）にする。各ドライバーの表が `Action` を網羅していることは、`match` の網羅性で保証する。D-17 (5) は、これより先の扱い（起動時に知らせるか、など）を決める。

## 3. 理由

- 実機が無くても、デバイスとのやり取りの手順をテストできる。E00 で分かった手順（`Ready!` を待つ、`k` を待つなど）は間違えやすく、ここが壊れると実機が止まらない・動かない、につながる。
- 境界を `Action` にすれば、デバイスや通り道を替えても、上の層とそのテストが変わらない（USB を Bluetooth に替える、Bittle を別のロボットに替える）。別のロボットで、`Action` の意味が同じになるか（例: 歩き方を送り直す必要があるか）は、ロボットごとにドライバーが吸収する（推論。替えるときに確かめる）。
- `Link` と `Clock` を `walk-core` に置けば、クレートを増やさずに済み、依存の境界（`cargo xtask deps` の照合の表）も変えなくてよい。

## 4. 検討して採らなかった案

- **今のまま（ドライバーがシリアルポートを直接持つ）**: 手順のテストに実機が要る。E00 の後では、手順が増えたので採らない。
- **境界を `Token` のままにする（Bittle 互換のデバイスと通り道だけを差し替えられる）**: 別のロボットに替えると `walk-core` が変わる。オーナーが `Action` を選んだので採らない。
- **`Link` を別のクレート（例: `walk-link`）に置く**: `std::io` をそのまま使えるが、クレートと依存の境界が増える。`walk-core` に `no_std` で置けるので採らない。置けないと分かったら見直す。
- **どこでも `dyn` を使う**: ドライバーの中はジェネリクスで十分で、実行時に選ぶ必要があるのは `walk-app` の組み立てだけなので、`dyn` はそこだけにする。
- **既存の HAL（例: 組み込み向けの `embedded-hal`）の trait を使う**: マイコン向けの形で、Mac の上のシリアルや HTTP、Jev の API には合わない（推論）。依存も増えるので採らない。

## 5. 影響

- [02](../02-architecture.md): 2.3節「ドライバー層」（要点とこの ADR へのリンク）を足し、2節の表（`Token` と動作→トークン表を `walk-bittle` へ）、3節のスケッチ（`Transport::send(Action)`、`Link`・`Clock`、長さの型）、4節の時計の扱いを直す（この ADR と同じ PR）。
- [05](../05-arbitration.md): P5 を「`Command` は必ず `Action` の並びに展開できる」に直す（この ADR と同じ PR）。
- [06](../06-transport.md): `SerialTransport` と `HttpTransport` を Bittle のドライバーとして位置づけ、「送れるのは `Token` だけ」を2段の許可リストに直す（この ADR と同じ PR）。
- D-05（スキルの形式）: フェーズ 1a の見直しで、`Action` の並びにする方向で決め直す。
- `walk-testing` に `FakeLink` を足す（実装の PR）。
- `docs/rules/coding.md`・`testing.md`・`documentation.md`・`review.md`（safety-reviewer の対象にある `walk-core` の `Token`・トークン表）: ドライバーとリンクの書き方と、ADR という文書の位置づけ（詳細は ADR、状態は decisions.md）を、別のルールの PR で足す。
- `cargo xtask deps` の照合の表: 変えない（クレートを増やさないため）。
